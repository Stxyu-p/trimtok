# Proposal: trimtok long-horizon usage log — 2026-10-12

Status: SHIPPED as Proposal 1 (same day). `usage.jsonl` + `/trimtok usage`
live in `__init__.py`; tests in `tests/test_core.py`; config `usage_enabled`
in `plugin.yaml`; README updated.

## Goal

Every prompt's trimtok activity becomes durable use-case data for future
development: which shapes fold, which revert, which originals get retrieved,
which commands dominate. The existing `audit.jsonl` answers "how much saved"
but not "what was it, and did the fold hold up".

## What exists today (do not duplicate)

- `audit.jsonl` (+`.1` rotation, 1MB cap): per-ok-transform `{tool, command?,
  kind, before/after/saved_chars, gate:"ok", hash, ms}`. Revert/passthrough
  gates are NOT logged. No content shape, no retrieval events.
- `trimtok_col.json` / stress tables: one-off lab numbers, not live data.
- `ccr_stats()` entries+bytes: cache size only, no per-shape breakdown.

## Proposal 1 (recommended): usage.jsonl alongside audit.jsonl

**What:** one JSON object per hook invocation — ok, revert, AND passthrough —
appended to `usage.jsonl` in the same plugin-data dir, same rotation shape as
audit (1MB cap + `.1`), same never-raises discipline.

**Where:** `__init__.py` `_on_transform` / `_on_tool_result` / `_handle_retrieve`
(one shared `_usage()` helper, mirroring `_audit`).

**Record shape (fixed keys, bounded):**

```json
{"ts": 1729, "hook": "terminal|tool|retrieve", "cmd": "pytest -q",
 "tool": "search_files", "kind": "log|diff|text|result",
 "gate": "ok|reverted_gate|reverted_quality|passthrough_*",
 "before": 141779, "after": 9200, "saved": 132579,
 "partial": true, "omitted": 2799, "ms": 33.7, "hash": "abc123def456",
 "shape": "err-dense|repeat|json|unique|mixed",
 "note": "retrieve|rerun|first-seen"}
```

- `shape`: cheap classifier (err-line ratio, repeat-run ratio, JSON-head) —
  NOT content, NOT prompts. Privacy: commands truncated to 120 chars like
  audit; no file bodies, no prompt text, ever.
- retrieve events log `{hook:"retrieve", hash, hit:true|false, slice:(offset,limit)|grep?}`
  — this closes the loop: fold rate vs retrieve rate tells whether folds are
  too aggressive (hot recall = show more next time).

**Why:** answers the three long-horizon questions audit cannot: which shapes
dominate real sessions (feeds Drain/shingle/HEAD_TAIL priority), whether
folds hold (retrieve rate per shape), which gates misfire (revert rate per
command/kind). Lean-ctx documents this gap honestly: its shadow-mode savings
are simulated estimates, not measured runs — we would have measured runs.

**Tradeoffs:**
- Pro: use-case corpus grows on its own; every future fold ships with evidence.
- Con: one more bounded file (~same size class as audit); one classifier to maintain.
- Risk: shape classifier drifts from real fold reasons — mitigate by deriving
  it from the same flags the fold already computed (forced count, hidden,
  minify_saved), not a second opinion.

**Effort:** Small (< 1 day, incl. tests).

## Proposal 2 (smaller): log reverts + retrieves only

**What:** keep audit.jsonl for ok-transforms; add two minimal streams:
revert/passthrough gate counts per (command, kind), and retrieve hit/miss per hash.

**Where:** same three hook sites, smaller record (no shape classifier).

**Why:** 80% of Proposal 1's value (where folds fail + whether they hold) at
~30% of the code. Shape breakdown can be recomputed later from CCR originals
by hash join.

**Tradeoffs:**
- Pro: smallest diff; no classifier to drift.
- Con: no per-shape priority signal until someone joins hashes offline.
- Risk: offline join rots (TTL expires originals) — acceptable, trends survive.

**Effort:** Small (< half day).

**Persona notes:**
- Contrarian: does the shape field earn its keep day one? Honestly not until
  Drain/shingle land — Proposal 2 defers it cleanly.
- Simplifier: this IS the simpler version. Pick this if Proposal 1 feels heavy.
- Architect: still feeds the ratchet (retrieve events are the regret signal).
- Hacker: just count gates in memory and dump on session end — no, crashes lose it.

## Proposal 3 (deferred): use-case miner + report command

**What:** `/trimtok usage` — top commands by saved chars, top revert shapes,
hottest retrieved hashes, suggested next fold, all from usage.jsonl.

**Where:** `_handle_ts_command` + one aggregator. NOT proposed for now —
needs 1-2 weeks of live usage data first, otherwise it reports lab fixtures.

**Effort:** Medium (after data accumulates). Park until then.

## Recommendation

Ship Proposal 2 now (revert + retrieve visibility, tiny diff), promote to
Proposal 1's shape field when Drain/shingle work starts and needs priority
signal. Proposal 3 waits for live data.
